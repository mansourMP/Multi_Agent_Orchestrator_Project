# Empyralis Surface Parity Contract

## Purpose

This document locks the cross-surface parity rule for Empyralis.

It answers one question exactly: how do mobile and platform or desktop remain the same platform without collapsing into identical navigation or identical control density.

If an implementation path, UI shortcut, or later memo implies that mobile is a weaker agent environment or that desktop is a separate brain, this document wins.

## Surface Parity Rule

Empyralis is one platform with multiple surfaces.

Mobile and platform or desktop must therefore share:

- the same engine
- the same Sage identity
- the same specialist model
- the same memory model
- the same runtime-placement model
- the same policy model

Surface differences are allowed only in how much control, density, and operational depth is exposed to the user.

Surface differences are not allowed to redefine agent capability.

## Shared Platform Contract

The shared platform contract is:

- same account and identity model
- same workspace model
- same app and agent contracts
- same runtime-selection behavior
- same memory visibility rules
- same specialist capability model
- same approval and policy rules

If a mobile request, desktop request, or app-originated request is otherwise equal in policy and runtime availability, it must resolve to the same execution semantics.

## Capability Determinants

Agent capability is determined by:

- runtime availability
- policy
- connector scope
- memory scope
- approval state

Agent capability is not determined by:

- mobile origin
- desktop origin
- whether the action started in an app surface
- whether the user is on a smaller screen

## Identical Cross-Surface Contracts

These contracts must remain identical across mobile and platform or desktop:

- identity model
- workspace model
- Sage orchestration model
- specialist power model
- specialist memory boundaries
- application runtime contracts
- runtime routing behavior
- approval semantics
- policy enforcement semantics
- auditability

## Allowed Surface Differences

These differences are allowed:

- navigation structure
- information density
- control depth
- builder ergonomics
- admin and debug ergonomics
- inspection depth

Desktop-power surfaces may expose richer controls for:

- runtime attachment management
- memory and privacy configuration
- specialist builder flows
- deeper activity review
- debug and admin depth

Those are control-depth differences, not intelligence differences.

## Forbidden Surface Divergence

The following are explicitly forbidden:

- weaker execution because the request came from mobile
- weaker specialists because the request came from an app flow
- different backend semantics for mobile versus desktop
- hidden mobile-only memory restrictions that are not policy-driven
- hidden desktop-only power paths that bypass the normal runtime and policy system
- UI-origin-based capability downgrades

If a capability is unavailable, the reason must be real:

- the runtime is unavailable
- policy denies it
- the connector is not allowed
- the memory class is not allowed
- approval is still required

## Application Parity Under One Platform

Applications remain product modules under the same platform contract.

That means:

- mobile may be the primary everyday consumer application surface
- desktop may expose deeper management and inspection views
- application backend semantics remain identical across surfaces
- application execution contracts remain identical across surfaces
- applications do not gain or lose intelligence because of which surface invoked them

Applications still do not inherit Sage memory or specialist memory by default.

## Sage And Specialist Parity

Sage and specialists remain cross-surface entities.

They therefore keep:

- the same orchestration model
- the same power model
- the same runtime-routing model
- the same memory-boundary model

Mobile may surface those capabilities more compactly, but it must not redefine them.

Desktop-power surfaces may expose more configuration and inspection, but they must not become a second brain.

## Product Interpretation

The correct interpretation is:

- one platform
- one Sage
- one specialist system
- one memory and policy system
- one runtime contract
- different surface density

This is how Empyralis avoids becoming:

- a weak mobile shell
- a desktop-only power product
- two different products sharing a logo
