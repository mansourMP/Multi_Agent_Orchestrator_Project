# Empyralis Internal Product Spec v2

## 1. Product definition
Empyralis is an AI operator that builds, runs, and monitors automations for you.

The product is not primarily:
- a workflow IDE
- a control panel
- a plugin marketplace
- a vertical app company

Those can exist inside the system, but they are not the core identity.

---

## 2. Product promise
A user should be able to:
1. describe what they want in plain language
2. see Empyralis turn that into a workflow
3. test it
4. activate it
5. monitor it clearly

This is the core promise of the product.

---

## 3. Core product model

### Core platform
The platform consists of:
- Assistant
- Automations
- Activity
- Files
- Connections
- Settings

### Capability layer
The platform works through:
- workflows
- tools
- skills
- connectors
- scheduling
- execution
- approvals

### Packaging layer
Optional packaged experiences may exist as:
- Solutions
- Packs
- Templates

These are wrappers around the core platform, not the foundation.

---

## 4. Primary user journey
The primary journey is:

1. user opens Assistant
2. user asks for work
3. Empyralis builds workflow visually
4. user reviews/edit if needed
5. user tests once
6. user activates
7. user monitors status

If a feature does not support this journey, it is secondary.

---

## 5. Navigation model

### Main navigation
- Dashboard
- Assistant
- Automations
- Activity
- Files
- Connections
- Solutions
- Settings
- Account

### Rules
- Dashboard is summary only
- Assistant is the main product surface
- Automations is the workflow library
- Activity is run history and current work
- Files is outputs and evidence
- Connections is tool/account setup
- Solutions is packaging only
- Settings is preferences only
- Account is identity only

### Admin/debug
Admin routes may exist, but are secondary:
- health
- approvals internals
- setup internals
- control-center style diagnostics

These must not define the normal product experience.

---

## 6. Route rules

### `/`
Purpose:
- Dashboard
- overview only
- recent activity
- recent automations
- clear status summary

Must not:
- behave like assistant chat
- behave like admin
- be the place where workflows are built

### `/workspace`
Purpose:
- main product surface
- assistant + live workflow building
- the primary “do work” screen

Layout target:
- left = assistant
- right = workflow/canvas
- optional drawer = inspector / details

This is the most important screen in the product.

### `/workflows`
Purpose:
- automation library
- open existing workflows
- create from template or assistant draft
- manage active/draft state

### `/solutions`
Purpose:
- packaged use cases built on top of the platform
- not the platform identity

### `/settings`
Purpose:
- preferences only

### `/account`
Purpose:
- profile only

---

## 7. Workflow product rules

### Workflows are the real engine
Everything in the platform should be representable through:
- workflows
- tools
- connectors
- scheduling
- actions

### Workflow building principles
- default method = ask assistant
- advanced method = edit visually
- visual graph must feel premium and readable
- graph must never feel like a debug view
- test and activation must be obvious

### Canvas requirements
- node search
- strong visual connections
- readable node cards
- clear handles
- clear selection state
- simple config editing
- clean test/run path

### Visual standard
Borrow from:
- n8n connection quality
- Activepieces simplicity
- Langflow / Flowise AI workflow feel

Do not clone products literally.

---

## 8. Solutions rules

### What a solution is
A solution is:
- a packaged workflow/tool experience
- a preset use case
- an optional wrapper

### What a solution is not
A solution is not:
- the platform identity
- the core shell
- the default home experience
- the nav foundation

### Rule
If a solution disappears tomorrow, the core platform must still make complete sense.

## 10. Design rules

### Product look
- premium
- minimal
- obvious
- calm
- high-contrast hierarchy
- low clutter

### UX rules
Every important screen must answer:
1. What is this?
2. What can I do here?
3. What should I do next?

### Red lines
- no duplicate nav concepts
- no empty placeholders without guidance
- no multiple competing primary actions
- no admin jargon on user screens
- no solution-specific buttons in the core shell
- no web chat keyword shortcuts
- no confusing route identity

---

## 11. Technical architecture rules

### Correct architecture
- assistant-first surface
- workflow-native core
- tools/skills/connectors beneath it
- solutions above it as packaging

### Avoid
- app marketplace architecture
- hardcoded vertical core
- building logic that only works for one solution
- special-case UI paths that bypass the product model

### Principle
If a capability is real, it should ultimately map to:
- a workflow
- a tool
- a connector
- an execution state

---

## 12. Frontend quality rules

### Required before shipping a surface
- clear purpose
- one dominant action
- responsive layout
- no hydration mismatch
- no route-specific weirdness
- no duplicate buttons
- no inconsistent branding
- no stale demo data

### Workflow canvas quality bar
- visually credible
- smooth rope-like edges
- consistent nodes
- correct selection/hover behavior
- professional spacing
- stable graph interactions

## 16. Decision rule for future work
Before building a feature, ask:

1. Does this strengthen the core product model?
2. Does this make Assistant → Workflow → Activate clearer?
3. Does this belong in core, or is it solution packaging?
4. Would a first-time user understand this immediately?
5. Is this adding clarity, or just adding surface area?

If the answer is weak, do not build it yet.

---

## 17. Final principle
Empyralis should feel like one capable AI operator with a visible workflow brain.

Not:
- a tool dump
- a plugin store
- a debug dashboard
- a vertical-specific shell

The product should feel:
- simple on the surface
- powerful underneath
- trustworthy immediately

---

## 18. v1 non-goals
These are explicitly out of scope for the core v1 product.

- plugin marketplace
- public extension ecosystem
- many vertical-first home experiences
- provider/model selection as a primary user task
- operator/debug surfaces as part of normal onboarding
- trying to match every n8n feature before the core flow is excellent

The goal is not “feature parity with everything”.
The goal is one excellent core product flow.

---

## 19. Build order
This is the required implementation order unless there is a strong reason to deviate.

### Stage 1 — Assistant workspace
Ship the main product surface first:
- left assistant
- right live workflow/canvas
- clear test action
- clear activate action
- clear connector prompt only when required

### Stage 2 — Workflow canvas quality
Make the canvas feel credible:
- rope-quality edges
- readable node shells
- clean drag/connect behavior
- condition branching
- better inspector

### Stage 3 — Dashboard reduction
Make `/` summary-only:
- recent automations
- recent activity
- useful status
- no workflow-building responsibility

### Stage 4 — Automations library
Make `/workflows` the management surface:
- open/edit existing workflows
- create new workflow
- view draft/active state
- clean metadata

### Stage 5 — Connections
Make setup human-readable:
- clear tool purpose
- clear next step after connect
- minimal technical language

### Stage 6 — Solutions
Keep solutions optional and secondary:
- packaged examples
- not the identity of the product
- removable without breaking the core story

---

## 20. Definition of done for a product surface
A surface is not done until all of these are true:

- purpose is obvious in under 5 seconds
- there is one dominant primary action
- empty state explains what to do next
- copy is plain English
- no internal jargon leaks through
- mobile and desktop both work
- no hydration or route-state bugs
- no duplicate concepts in nav or layout
- first-time user can continue without asking for help

If any one of these fails, the surface is not done.

---

## 21. Definition of done for workflow creation
Workflow creation is not done until a first-time user can:

1. ask for an automation
2. see the workflow appear visually
3. understand the basic graph without explanation
4. test it once
5. activate it
6. know where to monitor it afterward

If a user needs to understand internal setup concepts before this, the flow is not done.

---

## 22. Team operating rule
Before implementing a feature, the team must classify it as exactly one of:

- Core platform
- Workflow engine
- Connections
- Solution packaging
- Admin/debug

If classification is unclear, implementation should stop until it is clarified.

This prevents product drift.
