**Durability Truth Table**

| Flow | Verdict | Reason |
|---|---|---|
| Live run registration | Weak | Memory first, initial durable failure swallowed. |
| Pre-terminal live-run status | Weak | Async snapshot writes plus last-write-wins upsert. |
| Terminal archived run | Moderate | Sync archive is stronger, but surrounding side effects are not atomic. |
| Approval request | Weak | Pending state and event emission are not atomically durable. |
| Approval resolution | Weak to moderate | Durable side-table row exists, but live-run convergence is delayed and cross-process unsafe. |
| Runtime outbox storage | Moderate | Durable queue exists with retries/poisoning, but no row claim. |
| Telegram final delivery | Weak to moderate | Replay-safe only if receipt/state persistence survives after send. |
| WhatsApp final delivery | Weak | Same replay window, plus no provider idempotency input. |
| Local companion claim/release | Weak | Ownership split across memory, SQLite, and async Postgres writes. |
| Checkpointed local-run recovery | Moderate | Explicit recovery exists, but non-checkpoint orphan paths lag. |
| Direct chat continuity | Moderate | Interrupted replay only, single-worker requirement. |
| Session/thread continuity | Weak to moderate | Durable mirroring can preserve stale thread binding. |

**Highest-Risk Restart / Retry Hazards**
- Duplicate Telegram or WhatsApp finals if more than one outbox poller hits the same DB.
- Duplicate channel replies after provider success but before connector-state or receipt persistence.
- Approval resolved durably while `live_runs` and `/approvals` remain stale.
- Local companion stale claims being recreated or erased by late async claim/release writes.
- Lost live runs when initial registration persistence fails before a later durable snapshot.
- Startup recovery missing expired claims during transient DB failure, then never retrying full cleanup in that process.
- Repo-based activity/approval feeds missing events because the first write landed without full scope and later upserts do not repair scope columns.

**Confirmed Findings**
- The system has a real durable outbox and real checkpoint/local recovery logic.
- Terminal archived run persistence is materially stronger than live-run persistence.
- Critical correctness still depends on process memory and background writes in multiple paths.
- Channel delivery is replayable, but not exactly-once and not transport-idempotent.
- Approval durability is split between stronger side-table rows and weaker live-run convergence.
- Local companion ownership and recovery are only mostly-safe, not transactionally durable.
- Direct chat restart behavior is interruption replay, not full continuation.

**Unproven Suspicions**
- Non-channel outbox sinks may also duplicate under multi-poller races, but I did not trace every downstream sink to user-visible duplication.
- Some stale local-claim situations may self-heal through later watchdog cleanup, but the worst-case convergence delay depends on runtime traffic and heartbeat timing.
- The process-local approval lock likely worsens under true multi-worker deployment beyond the exact duplicate-resolve path proven here.
